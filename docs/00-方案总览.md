# 图书馆自习座位实时助手 —— 方案总览 v0.1

> 一句话：**用我们自己装的摄像头，把"现在哪个座位空着、什么时候来最容易有座"做成一个扫码即用的网页。**

---

## 0. 先说三个决定成败的前提

在聊技术之前，先把三件最容易翻车的事说清楚，后面所有设计都围绕它们：

1. **授权比技术难。** 自己在阅览室天花板上打孔装摄像头，图书馆大概率会拦。真正的破局点不是"更聪明的算法"，而是**把产品包装成"给图书馆的管理工具"**——学生端找座位只是顺带功能。图书馆获得：区域利用率报表、闭馆/开区域的决策依据、高峰期数据。你获得：点位、供电、网络、合法身份。这一点决定了项目能否落地，比选什么模型重要 10 倍。
2. **隐私是红线，也是设计约束。** 《个人信息保护法》第 26 条规定，公共场所的图像采集设备**应当为维护公共安全所必需**，收集的个人图像只能用于公共安全目的。用监控做"座位统计"严格讲不算公共安全，所以必须走**"不构成个人信息"**的路线：本地处理、不存原始视频、不出设备、画面里尽量不出现人脸。这套设计不是合规负担，反而是说服图书馆的最有力材料。
3. **摄像头看到的是"人"，不是"座位"。** 所有算法难点都来自这句话：人站起来走了但书包还在、两个人挤一个座、有人站在过道聊天、坐着的人挡住后面一排。方案必须正面处理这几种情况，否则上线第一天就会被同学骂"不准"。

## 2. 一个被低估的捷径：先看图书馆有没有现成数据

去问两件事，能省掉一半工作量：

1. **有没有座位预约系统？**（很多高校用超星/学习通/自研小程序的"座位预约"）
   - 有 API 或数据库只读权限 → 直接拿到"谁约了哪个座"，摄像头只用来做**"预约了但没人来"的核验**。这个组合比纯视觉准得多，而且图书馆有动力配合（他们在意的是占座率）。
   - 没有 API → 也能做，但别去爬，走正式合作。
2. **有没有门禁/闸机的进出人数？** 有的话可以做总量校验，视觉只负责"座位级"分布。

## 3. 系统架构

```
┌─────────────────────────── 场馆侧（边缘） ───────────────────────────┐
│                                                                      │
│  [相机1 RTSP] ─┐                                                     │
│  [相机2 RTSP] ─┼→ FFmpeg/GStreamer 解码 → 1 fps 采样                  │
│  [相机3 RTSP] ─┘        │                                            │
│                         ▼                                            │
│              YOLO 人体检测 + ByteTrack 跟踪                           │
│                         │                                            │
│                         ▼                                            │
│          座位多边形归属（脚点落在哪个座位区）                           │
│                         │                                            │
│                         ▼                                            │
│        每座位状态机（带迟滞：20s 判占用 / 3min 判离开）                 │
│                         │                                            │
│                         ▼                                            │
│              状态聚合 → MQTT / HTTPS（只传 JSON，不传画面）            │
└─────────────────────────┬────────────────────────────────────────────┘
                          │  只传 {"seat":"A-12","state":"free","conf":0.93,"ts":...}
                          ▼
┌──────────────────────────── 后端 ────────────────────────────────────┐
│  FastAPI  ←  WebSocket 推送 / REST 查询                               │
│     ├─ Redis：最新状态缓存（读多写多，别压 DB）                        │
│     ├─ PostgreSQL + TimescaleDB：状态历史、5 分钟聚合、预测结果         │
│     └─ 定时任务：每 5 分钟聚合 + 每小时重算预测基线                     │
└─────────────────────────┬────────────────────────────────────────────┘
                          ▼
┌──────────────────────────── 前端 ────────────────────────────────────┐
│  Next.js + React 座位地图（SVG）+ 空位曲线 + 订阅                     │
│  移动端优先 PWA，扫码即用，无需登录                                    │
└──────────────────────────────────────────────────────────────────────┘
```

**关键设计取舍：**

- **视频不出场馆。** 边缘盒子只上传布尔状态。这既是隐私要求，也让带宽降到几乎为零（一个房间一小时 < 1 MB）。
- **采样 1 fps 就够。** 座位变化是分钟级的，不需要 30fps。算力因此降 30 倍，一台树莓派都能跑一个房间。
- **端到端延迟目标 15 秒内。** 超过 30 秒，用户就会觉得"这网站是假的"。
- **状态机比模型重要。** 模型给的是"这一帧有没有人"，产品要的是"这个座位现在算不算被占"。中间那层逻辑（迟滞、遮挡处理、置信度）决定了 80% 的体验。

## 4. 摄像头方案（你问的重点）

### 4.1 为什么不能接图书馆监控，以及三条替代路线

图书馆的监控系统：NVR 私有协议、内网隔离、有《安全技术防范》管理规定、涉及全馆所有区域的人员影像。**不要试图接，也不要试图要密码。** 技术上能接也绝对不该接——那会让你从"做个小工具"变成"非法获取监控数据"。

替代路线只有三条：

| 路线 | 做法 | 现实可行性 |
|---|---|---|
| **A. 自带相机，装在"我们的"位置** | 相机架在书架顶、隔断上、窗台、移动三脚架上，用夹具不打孔 | ★★★★ 最推荐，先谈授权 |
| **B. 与图书馆共建** | 以"管理工具"名义，让图书馆出点位和电，你出设备和软件 | ★★★★★ 长期最优 |
| **C. 完全绕开场地** | 只做数据产品：接入预约系统数据 + 用户众包上报 | ★★ 精度差，但零硬件 |

**建议**：用 A 做 2 周概念验证（拿数据说话），拿验证结果去谈 B。C 作为兜底。

### 4.3 相机的"参数"到底看什么

买相机别看"像素越高越好"，看这五项：

| 参数 | 要求 | 为什么 |
|---|---|---|
| **分辨率** | 4MP（2560×1440）起步，4K 更好 | 见下方算账，4MP 已经余量很大 |

> **例外**：15 座以内、视线距离 6m 的小房间，1080p 完全够用（约 100 px/m）。
> 试点阶段别为 4K 多花钱，见 [01-试点执行手册](01-试点执行手册.md)。
| **镜头焦距** | 定焦 2.8mm（≈100° 视场）或 4mm（≈80°） | 定焦！**绝对不要 PTZ 云台**——镜头一漂，座位多边形全废 |
| **宽动态 WDR** | ≥ 120 dB | 阅览室窗户逆光，没有 WDR 靠窗座位会变成一片死黑 |
| **低照度** | ≤ 0.01 lux，或带红外 | 晚上自习到 22:30，很多馆灯光偏暗 |
| **协议** | 必须支持 **RTSP + ONVIF**，且能关掉厂商云/P2P | 这是"不依赖厂商 App、数据不出内网"的前提 |

**分辨率算账（别被"4K 才够"忽悠）：**

- 层高 3m，相机装 2.9m，俯角 35°，到最远座位斜距约 5.5m。
- 2.8mm 镜头 4MP，水平视场 ≈104°，5.5m 处横向覆盖 ≈ 14m，像素密度 ≈ 2560/14 ≈ **180 px/m**。
- 一个坐着的人肩宽 0.45m → **约 80 像素**。YOLO 检测下限约 20–30 像素。
- **结论：4MP + 2.8mm，一台覆盖 60–100 m²（约 20–35 个座位）。** 200 m² 的阅览室 2–3 台足够。
- **真正的瓶颈不是分辨率，是遮挡和视角。**

### 4.4 点位：这一步做错，后面全白干

**四条硬规则：**

1. **装在走道尽头，沿走道看，不要正对桌面。** 沿排间走道俯视，每个人至少露出头和肩，且相邻座位处于不同景深，遮挡最少。正对一排桌子拍，前排人会完整挡住后排。
2. **俯角 35°–50°。** 太平（<30°）遮挡严重且拍到脸；太陡（>60°）只能看到头顶和桌面，反而难判断"人是否坐着"。
3. **高度 2.6–3.2m。** 低于 2.5m 容易被走动的人挡住；高于 3.5m 视角太陡。
4. **避开窗户正对方向。** 逆光会让靠窗区域过曝。实在避不开，靠 WDR + 手动曝光锁定。

**勘察清单（拿手机去现场，20 分钟做完）：**

- [ ] 画一张区域平面图，标出每个座位编号
- [ ] 找出可固定的位置：书架顶、隔断上沿、柱子、窗台、空调检修口旁
- [ ] 每个候选点位拍一张"相机高度视角"的照片，检查：能看清几个座位？被什么挡住？
- [ ] 记录光照：白天/晚上各拍一次，看逆光
- [ ] 记录电源和网口位置，量线长
- [ ] 问清楚：能不能打孔？能不能粘？消防有没有要求？

### 4.5 网络与供电

- **PoE 是首选**：一根网线同时供电+传数据，最省事。PoE 交换机放在弱电间或书架上。
- **WiFi 相机的坑**：IP 会变（要在路由器上做 DHCP 静态绑定）、夜间断流、2.4G 拥塞。能用有线就别用 WiFi。
- **网络隔离**：相机单独一个 VLAN 或至少单独 SSID，只允许边缘盒子访问，禁止相机出公网。改掉默认密码，关掉 UPnP 和 P2P。
- **外网访问**：校园网通常没有公网 IP。方案：(a) 边缘盒子直接跑 Web 服务，场馆 WiFi 内访问（最简单）；(b) frp / Cloudflare Tunnel 打洞；(c) 只把状态 JSON 推到云服务器，前端在云上。推荐 (c)，最稳且最符合隐私设计。

### 4.6 隐私设计（写进方案，也是谈判筹码）

| 措施 | 说明 |
|---|---|
| **本地推理，不存视频** | 画面进 GPU 出结果，原始帧不落盘。调试期最多保留 24h 加密片段，之后自动删除 |
| **只输出布尔值** | 上传的只有 `{"seat":"A-12","state":"free"}`，没有图像、没有 ID |
| **不做人脸识别** | 明确写进产品说明。也**不要**做"某同学今天学了多久"这类个体行踪统计——那是敏感个人信息 |
| **画面裁剪** | 在相机或边缘端把画面下沿以上的人脸区域 mask 掉，只保留桌面/椅面/上半身轮廓 |
| **公示牌** | "本区域安装有座位统计摄像头，仅统计座位占用情况，不采集人脸、不存储视频"，附联系人 |
| **书面同意** | 与图书馆签一页纸的数据处理说明，明确目的、范围、期限、删除方式 |
| **可审计** | 保留数据流图和处理日志，学校信息办大概率会要 |

> 如果只能记住一句：**这个系统里不应该存在任何能指向"某个具体的人"的数据。**

## 5. 算法方案

### 5.1 两条技术路线，建议都留

**路线 A：人体检测 + 座位多边形（MVP 用这条）**

```
帧 → YOLO 检测人体 → ByteTrack 跟踪 → 取 bbox 底边中点（脚点）
   → 判断落在哪个座位多边形内 → 该座位记一票 → 状态机
```

- 优点：**不需要训练**，COCO 预训练的 YOLO 直接能用；换场地只要重画多边形；当天就能跑。
- 缺点：遮挡时漏检；书包放椅子上会被误判（因为这个方案只看"人"，不看"物"）。

**路线 B：座位级 ROI 分类器（第二期提精度）**

- 对每个座位裁一块固定 ROI（桌面+椅面），输入一个小 CNN（MobileNet/EfficientNet-lite），输出 `empty / person / belongings / ambiguous`。
- 优点：天然处理"人走了书包还在"；对遮挡更鲁棒；**隐私更好**（模型只看桌面那一小块，画面里根本没有脸）；小模型快。
- 缺点：每个场地要标 1000–2000 张图（半自动：用路线 A 的结果预标注，人工只改错的）。
- **建议：A 上线拿数据 → 用 A 的结果自动标注 → 训 B → A+B 投票。**

**必须处理的三类硬 case：**

| 情况 | 处理 |
|---|---|
| 人站起拿书，30 秒后坐下 | 状态机迟滞：连续 3 分钟无人 → 才判"空" |
| 书包占座，人不在 | 路线 B 的 `belongings` 类；或标为"暂离"，不显示为空 |
| 两人挤一个座 / 一人占两座 | 以人数计席位，不按座位块；`occupied_seats = min(person_count, seat_count)` |
| 站在过道聊天 | 脚点不在座位多边形内 + 停留时间 < 阈值 → 不计入 |
| 相机被挡住/离线 | 整块区域标"数据不可用"，**绝不显示"全空"**（这是最容易踩的坑） |

### 5.2 座位状态机

```
UNKNOWN ──(连续 20s 检测到同一 track 在座)──→ OCCUPIED
OCCUPIED ──(连续 180s 无人体)──→ EMPTY
OCCUPIED ──(无人 + 检测到物品)──→ AWAY（暂离，显示黄色）
任意 ──(遮挡/离线/置信度低)──→ UNKNOWN（灰色）
```

迟滞窗口是可调参数，上线后用"用户纠错"数据来调。

### 5.3 "建议你什么时候来"怎么算

别一上来就上 LSTM。**这个场景里，简单方法能赢 90% 的复杂模型**，因为规律极强（作息、课表、考试周）。

**基线（第 1 周就能有）**

```
对同一星期几、同一 30 分钟时段，取最近 4 周的空位数中位数
→ baseline[weekday][slot]
```

**当日修正**

```
deviation = 最近 30 分钟实际空位数 - 同时段 baseline
对未来 2 小时做指数衰减外推：pred[t] = baseline[t] + deviation * exp(-t/90min)
```

**"值不值得来"**

```
P(到馆后 10 分钟内找到 ≥1 个座位) ≈ 用泊松/二项分布，λ = pred_free_seats
→ 页面直接显示"现在过来，约 78% 概率有座"
```

**最佳时间推荐**

```
在未来 3 小时的曲线上，找空位期望最大的连续 30 分钟窗口
对比"现在"：如果提升 > 20%，才建议"稍后再来"，否则别烦用户
```

**冷启动**：前 2 周只显示历史同星期均值，页面标注"数据积累中，预测仅供参考"。**诚实比假装聪明重要。**

如果之后要升级：LightGBM + 特征（星期、小时、是否考试周、天气、是否节假日）+ 分位数回归。但先跑通基线，别提前优化。

### 5.4 怎么衡量"准不准"

- 人工核对：每天 3 次（10:00 / 15:00 / 20:00），随机抽 1 个区域，逐座位记录真实状态。
- 指标：**座位级准确率**（目标 ≥ 90%）、**空位数误差**（目标 ±2 个以内）、**状态切换延迟**（目标 < 60s）。
- 上线后持续用"用户纠错"按钮算在线准确率，每周看趋势。

for frame in sampler(rtsp_url, fps=1):
    persons = yolo(frame)                       # [{bbox, conf}]
    tracks  = tracker.update(persons)           # 稳定 track_id
    for t in tracks:
        p = ((t.bbox[0]+t.bbox[2])/2, t.bbox[3])  # 脚点

## 9. 需要你确认的几件事

这些答案会显著改变方案，尤其第 1、2 条：

1. **场地性质**：是学校图书馆（有信息化部门、可能要审批），还是校外自习室/咖啡馆（老板点头就行）？
2. **能不能装**：天花板打孔、粘接、走线，哪样允许？有没有现成网口和插座？
3. **规模**：先做一个房间（20–40 座），还是一层楼（200+ 座）？
4. **你的技术栈**：Python 熟不熟？前端想自己写还是套现成模板？有没有 GPU 机器？
5. **预算与时间**：几百块试水，还是几千块做正式版？每周能投入几小时？
6. **有没有现成的座位预约系统**？能不能拿到数据？

## 10. 一页纸总结

- **产品**：扫码看座位地图 + 未来 3 小时空位预测 + 最佳到馆时间。
- **架构**：相机 → 边缘盒子（YOLO + 座位多边形 + 状态机）→ 只传状态 JSON → FastAPI + 时序库 → Web/WS。
- **相机**：**4MP 定焦 2.8mm、支持 RTSP/ONVIF、带 WDR、不要云台**；装走道尽头、俯角 35°–50°、高度约 3m；一台覆盖 60–100 m²。
- **验证**：先用现有笔记本 + 一个 USB 摄像头，2 周跑通单房间，拿到准确率报告再去谈授权和买设备。
- **红线**：本地推理、不存视频、不传画面、不做人脸、只输出座位状态。
